# Vibe Coding Daily Brew 產品轉型藍圖

> 文件狀態：產品轉型基準文件  
> 建立日期：2026-08-21  
> 初始產品：Vibe Coding Daily Brew  
> 轉型方向：從單一主題的每日摘要，轉為每個人都擁有自己的個人晨報與學習記憶系統

## 閱讀方式

- **已確立**：來自產品原始想法與目前已確認的產品價值。
- **建議**：為了達成產品目標而提出的產品或工程方案。
- **待決策**：需要之後由產品決定，不能假裝已經定案。

本文件保留產品最初的情緒來源：Vibe Coding Taiwan 社群每天出現許多有趣文章，但人們常常只能截圖、收藏，最後再也沒有回頭閱讀，因而產生 FOMO。這個問題不是「找不到內容」，而是「內容太多，沒有被選擇、理解、保存與記住」。

---

## 1. 產品轉型目的

### 現在

Vibe Coding Daily Brew 是一個以 Vibe Coding 為主題的每日摘要系統：收集近期內容，整理成固定數量的學習篇章，並提供收藏、知識儲藏室與歷史手沖。

### 轉型後

它要成為一份由使用者自己調配的晨報：

> 每天早晨，系統替每個人從開放網路中挑出「現在的他最值得讀的幾篇」，整理成可以理解、保存、複習與重新出現的學習內容。

初期仍然只做 Vibe Coding；架構上則預留未來加入設計、創業、研究、心理學等主題的能力。

### 核心轉換

```text
固定的 Vibe Coding 摘要
        ↓
個人的主題、來源、難度與閱讀口味
        ↓
個人化候選內容與排序
        ↓
每天一壺屬於自己的晨報
        ↓
收藏、回饋、複習與口味學習
```

## 2. 產品真正的價值

### 已確立的核心價值

產品的價值不是「網路上有免費文章」，因為文章本身已經太多。

真正的價值是四件事：

1. **幫使用者選擇**：不用每天追幾百則貼文。
2. **幫使用者理解**：把討論提煉成問題、原則、範例與限制。
3. **幫使用者記住**：收藏、複習、Second Pour。
4. **幫使用者形成口味**：慢慢知道他喜歡哪些主題、來源、難度與文章型態。

### 要完成的心理轉換

| 使用者現在的痛點 | 產品要提供的感受 |
| --- | --- |
| Feed 焦慮 | 安心的晨間儀式 |
| 截圖囤積 | 可搜尋的知識庫 |
| 隨機閱讀 | 個人學習循環 |
| 網路噪音 | 自己的晨報 |
| 害怕錯過 | 相信好內容會被保存與重新帶回來 |

### 最重要的產品判斷

產品不是要把文章找得更多，而是要讓每個人每天只看到：

> **現在的他，最值得讀的那幾篇。**

## 3. 產品定位與語言

### 英文定位

> **A personal morning newspaper for everything you want to learn.**

### 中文定位

> **每天一壺，替你把開放網路煮成自己的晨報。**

### 品牌語言

> **網路不停說，你不用一直追。**

### 對開放網路的主張

不要把主要宣傳寫成「不需要購買付費知識」。這會不必要地把產品放進與付費課程對立的位置。

更穩健的說法是：

> **在購買更多知識以前，先把開放網路上已經存在的好內容真正讀懂、保存並記住。**

付費內容仍然可能提供系統性、原創研究與專家經驗；本產品的價值是先替使用者處理開放網路中的選擇、上下文、理解與記憶問題。

### 使用者任務（Job to be Done）

> 當我早上想學點有用的東西時，給我一小批符合我現在興趣與程度、來源可追溯、今天真的讀得完，而且以後還能重新複習的內容。

## 4. 轉型原則

1. **選擇比數量重要**：不要因為每天內容很多，就把更多內容塞給使用者。
2. **證據先於摘要**：每篇學習內容都必須保留原始來源、日期與可檢查的證據。
3. **偏好是一份晨報配方**：偏好不是一個藏在設定頁的欄位，而是決定每一壺味道的配方。
4. **Prompt 不是權限系統**：Prompt 可以描述語意喜好，但硬性來源限制、排除規則與存取權限必須由程式實際執行。
5. **模型不是唯一的排序者**：模型負責理解與提煉；來源收集、硬性過濾、去重與證據檢查必須可驗證。
6. **每一壺都要被保存**：個人晨報不能只是一次 API 回應；必須可以重新載入、回顧與複習。
7. **回饋要改變下一壺**：Starred、Super Starred、不感興趣等動作都必須成為未來推薦訊號。
8. **先做 Vibe Coding，架構預留擴張**：不要一開始就做「所有知識」，先證明一個主題上的個人化體驗。
9. **API key 永遠留在伺服器端**：使用者偏好可以同步，金鑰不能暴露在前端或 Git。
10. **來源取得必須誠實**：無法合法或可靠取得的來源，就顯示無法取得，不要假裝讀過。

## 5. 目前系統與轉型缺口

### 目前已經具備的能力

- 今日手沖與固定篇數的學習內容。
- 偏好設定：來源權重、指定來源、額外 Prompt、硬性網址、語言。
- `/api/brew` 即時手沖。
- `server.mjs` 與 `api/brew.mjs` 的來源偏好與模型格式處理。
- Starred、Super Starred、知識儲藏室與歷史手沖。
- 難度標籤：初學者、普通、困難。
- 每日批次腳本與日期化輸出。

### 目前必須改變的地方

| 現在的做法 | 轉型後的做法 |
| --- | --- |
| 偏好主要存在瀏覽器 `localStorage` | 偏好成為使用者資料，`localStorage` 只作快取 |
| 每次手沖都可能重新生成 | 先建立並保存個人的 edition，再重新載入 |
| 全站共用 `latest.json` | 每位使用者、每天各自擁有一個 edition |
| 每日腳本產生單一批次 | 先建立候選內容池，再依使用者生成個人批次 |
| Starred 主要是收藏狀態 | 收藏、跳過與回饋會影響推薦排序 |
| 模型自行搜尋與整理 | 來源收集、驗證、排序與模型提煉分層 |
| 靜態頁面內含示範 lessons | 由個人 edition API 提供主要內容，保留示範資料作離線 fallback |

## 6. 目標生成流程

未來每一壺晨報應該遵循這條流程：

```text
使用者偏好與歷史回饋
        ↓
來源收集與候選內容池
        ↓
硬性過濾：日期、語言、網址、權限、排除項目
        ↓
證據檢查：URL、作者、日期、互動與來源完整性
        ↓
個人化排序：主題、來源、難度、新鮮感、複習與多樣性
        ↓
模型提煉：問題、原則、範例、限制、練習與證據
        ↓
結構化驗證與保存
        ↓
今日晨報、知識儲藏室與 Second Pour
```

模型只負責把已經選好的候選內容整理成學習素材，不應該完全自由決定所有來源、日期與證據。

### 個人化排序至少需要考慮

- Curator 基礎分數。
- 主題符合度。
- 來源偏好。
- 難度符合度。
- 新鮮程度。
- 是否讀過。
- 是否收藏。
- 是否該複習。
- 來源與類別多樣性。
- 使用者過去的「不感興趣」訊號。

### 必要的硬性檢查

- [ ] URL 可訪問或狀態明確標示。
- [ ] 發布日期正確。
- [ ] 不超過晨報資料截點。
- [ ] 不重複同一來源。
- [ ] 不重複同一個觀念。
- [ ] 每篇都有來源證據。
- [ ] 不捏造作者、日期、互動數據或引文。
- [ ] 輸出符合固定 JSON schema。
- [ ] 生成失敗時不發布 placeholder 內容。

## 7. 執行清單

### 第一階段：先定義「我的晨報」

- [ ] 保留 Vibe Coding 作為第一個主題，不一開始就做所有知識領域。
- [ ] 架構支援未來加入設計、創業、研究、心理學等主題。
- [ ] 定義預設晨報配方：
  - 6 篇符合偏好的新發現。
  - 2 篇過去收藏的複習。
  - 1 篇經典內容。
  - 1 篇意外驚喜。
- [ ] 讓使用者選擇每天閱讀時間：5、10、20 分鐘。
- [ ] 讓使用者選擇每天篇數：5、10、15 篇。
- [ ] 第一版不要讓使用者調整二十個參數。
- [ ] 第一版先詢問：
  - 我想學什麼？
  - 我不想看到什麼？
  - 我偏好的來源？
  - 我想要多難？
  - 我想要多少新鮮感？
  - 我是否想複習舊內容？

### 第二階段：把偏好變成真正的使用者資料

- [ ] 使用者帳號，或先建立穩定的匿名使用者 ID。
- [ ] 個人偏好資料表。
- [ ] 個人晨報資料表。
- [ ] 個人收藏與回饋資料表。
- [ ] 個人複習佇列。
- [ ] 使用者重新整理時載入原本的 edition，而不是重新生成。
- [ ] 將 `localStorage` 降級為本地快取，不再當正式資料來源。
- [ ] 個人資料與 API 金鑰分離。

### 建議資料結構

```text
users
profiles
preference_profiles
sources
user_sources
candidates
lessons
editions
edition_items
feedback_events
review_queue
generation_runs
```

最重要的定義：

```text
edition = 某一位使用者在某一天看到的那一壺晨報
```

不能再只有一個全站共用的 `latest.json`。

### 第三階段：重新設計偏好設定

「偏好」不只是設定頁，而是使用者的「晨報配方」。

- [ ] 主題權重：1–5。
- [ ] 來源權重：1–5。
- [ ] 指定來源。
- [ ] 排除來源。
- [ ] 指定社群或網址。
- [ ] 分開軟性偏好與硬性規則。
- [ ] 來源語言。
- [ ] 輸出語言。
- [ ] 難度。
- [ ] 閱讀時間。
- [ ] 新鮮內容與經典內容比例。
- [ ] 複習比例。
- [ ] 額外 Prompt。
- [ ] 不想再看到的主題。

明確區分：

```text
偏好：請多找 GitHub、少找 Reddit
硬性規則：只能從這幾個網址翻找
```

Prompt 可以處理「語意喜好」，但不能取代真正的過濾、排序與權限規則。

### 第四階段：把生成流程拆成四層

目前比較像：

```text
呼叫模型 → 模型搜尋 → 模型整理 → 回傳
```

未來應該是：

```text
來源收集
→ 候選內容池
→ 硬性過濾與證據檢查
→ 個人化排序
→ 模型提煉成晨報
→ 儲存
```

### 第五階段：建立來源連接器

建議順序：

1. GitHub Discussions、Issues、Repositories。
2. Hacker News。
3. Reddit。
4. RSS 與公開技術部落格。
5. 使用者自行提供的網址。
6. Facebook 公開頁面或有合法存取權限的內容。

Facebook 社團不能直接假設可以任意爬取。穩妥做法是：

- [ ] 使用者提供公開網址。
- [ ] 使用官方 API 或合法授權。
- [ ] 提供手動匯入連結。
- [ ] 對無法讀取的內容清楚顯示「無法取得」。
- [ ] 不假裝已經讀過無法驗證的社團內容。

### 第六階段：讓回饋真正影響下一壺

目前 Starred 與 Super Starred 主要是收藏功能。未來需要把它們變成推薦訊號：

- [ ] Starred：我想保存。
- [ ] Super Starred：這非常符合我的口味。
- [ ] 不感興趣：降低類似內容。
- [ ] 不想看這個來源。
- [ ] 想看更多這種內容。
- [ ] 已讀但不需要複習。
- [ ] 標記為想實作。

每個動作都記錄：

```text
使用者
內容
來源
主題
難度
動作
時間
```

系統最後要能理解：

> 這個人不是只喜歡 GitHub，而是喜歡 GitHub 上的實作失敗分析。

### 第七階段：做 Second Pour

這會讓產品從「摘要工具」變成「個人學習系統」。

簡單版本：

- [ ] Starred：7 天後複習。
- [ ] Super Starred：3 天、14 天、45 天複習。
- [ ] 普通內容：30 天後詢問是否還記得。
- [ ] 複習時只顯示一個 30 秒問題，不重新塞完整文章。
- [ ] 每篇顯示「你在 24 天前讀過這個」。

複習問題範例：

> 還記得這個原則解決什麼問題嗎？

## 8. 最推薦的開發順序

不要一開始就做完整的「全世界知識平台」。

### MVP 1：單一使用者個人化

- [ ] 個人主題。
- [ ] 個人來源權重。
- [ ] 個人難度。
- [ ] 個人晨報。
- [ ] 可保存與重新載入。
- [ ] Brew another pot。
- [ ] 仍然只支援 Vibe Coding。

### MVP 2：個人回饋

- [ ] Starred、Super Starred、不感興趣。
- [ ] 下一壺會依回饋改變。
- [ ] Pantry 與 Second Pour。

### MVP 3：真正多使用者

- [ ] 登入。
- [ ] 資料庫。
- [ ] 每人不同的 edition。
- [ ] 每人自己的歷史與複習資料。
- [ ] 時區與晨報時間。

### MVP 4：自動遞送

- [ ] 每日排程。
- [ ] Email 或通知。
- [ ] 失敗重試。
- [ ] 成本與使用量記錄。

### 推薦路徑

先完成 MVP 1，驗證「人們是否真的喜歡自己的晨報配方」；接著完成 MVP 2，驗證回饋是否能帶來更高的回訪與閱讀；最後才投入登入、資料庫與多人基礎設施。

## 9. 最小可驗收標準

當以下事情都成立，就有第一版真正的個人化晨報：

- [ ] 新使用者可以完成偏好設定。
- [ ] 兩個不同使用者得到不同內容。
- [ ] 相同使用者重新整理，不會重新生成另一壺。
- [ ] 使用者可以手動 Brew another pot。
- [ ] 每篇內容都有來源、日期、證據與難度。
- [ ] Starred 會影響下一次推薦。
- [ ] Super Starred 會進入複習佇列。
- [ ] 可按收藏、類別、難度瀏覽。
- [ ] 使用者的偏好不會暴露 API key。
- [ ] 生成失敗時不會塞入假文章或假來源。
- [ ] 個人晨報不再依賴 Git 裡的單一 `latest.json`。

## 10. 待決策事項

以下內容尚未定案，實作前需要明確選擇：

- [ ] 第一版是否需要登入，還是先使用匿名使用者 ID？
- [ ] 正式資料庫與身份驗證採用哪一種服務？
- [ ] 每日預設篇數是 5、10 還是 15？
- [ ] 預設晨報配方是否採用「6 新、2 複習、1 經典、1 驚喜」？
- [ ] 第一個外部遞送管道是 Email、通知，還是先只做網站內晨報？
- [ ] 複習間隔是否固定，還是允許使用者調整？
- [ ] Facebook 社團的第一版是否只接受手動 URL 匯入？
- [ ] 未來新增主題時，是否共用同一套來源、候選內容與學習資料模型？

## 11. 轉型成功的判準

產品成功，不是每天產出更多文章，也不是模型回覆得更長。

成功是：

> 使用者早上打開 Brew，覺得這壺內容像是「有人真的懂我現在想學什麼」；讀完之後，知道哪些內容值得保存，也相信重要的內容未來還會在適合的時候回來。

這就是從每日摘要系統轉型為個人晨報與個人學習記憶系統的核心。
