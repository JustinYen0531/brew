# Vibe Coding Daily Brew 產品轉型藍圖

> 文件狀態：產品轉型基準文件  
> 建立日期：2026-08-21  
> 初始產品：Vibe Coding Daily Brew  
> 轉型方向：從單一主題的每日摘要，轉為每個人都擁有自己的個人晨報與學習記憶系統

## 閱讀方式

- **已確立**：來自產品原始想法與目前已確認的產品價值。
- **建議**：為了達成產品目標而提出的產品或工程方案。
- **待決策**：需要之後由產品決定，不能假裝已經定案。

本文件保留產品最初的情緒來源：Vibe Coding Taiwan 社群每天出現許多有趣文章，但人們常常只能截圖、收藏，最後再也沒有回頭閱讀，因而產生 FOMO。真正卡住人的地方，是內容太多，還沒有被選擇、理解、保存與記住。

## 1. 產品轉型目的

### 現在

Vibe Coding Daily Brew 是一個以 Vibe Coding 為主題的每日摘要系統：收集近期內容，整理成固定數量的學習篇章，並提供收藏、知識儲藏室與歷史手沖。

### 轉型後

它要成為一份由使用者自己調配的晨報：

> 每天早晨，系統替每個人從開放網路中挑出「現在的他最值得讀的幾篇」，整理成可以理解、保存、複習與重新出現的學習內容。

初期仍然只做 Vibe Coding；架構上則預留未來加入設計、創業、研究、心理學等主題的能力。

### 核心轉換

```text
固定的 Vibe Coding 摘要
        ↓
個人的主題、來源、難度與閱讀口味
        ↓
個人化候選內容與排序
        ↓
每天一壺屬於自己的晨報
        ↓
收藏、回饋、複習與口味學習
```

## 2. 產品真正的價值

### 已確立的核心價值

網路上的免費文章很多；產品的價值落在選擇、理解、保存與記住。

真正的價值是四件事：

1. **幫使用者選擇**：不用每天追幾百則貼文。
2. **幫使用者理解**：把討論提煉成問題、原則、範例與限制。
3. **幫使用者記住**：收藏、複習、Second Pour。
4. **幫使用者形成口味**：慢慢知道他喜歡哪些主題、來源、難度與文章型態。

### 要完成的心理轉換

| 使用者現在的痛點 | 產品要提供的感受 |
| --- | --- |
| Feed 焦慮 | 安心的晨間儀式 |
| 截圖囤積 | 可搜尋的知識庫 |
| 隨機閱讀 | 個人學習循環 |
| 網路噪音 | 自己的晨報 |
| 害怕錯過 | 相信好內容會被保存與重新帶回來 |

### 最重要的產品判斷

產品要做的，是讓每個人每天只看到：

> **現在的他，最值得讀的那幾篇。**

## 3. 產品定位與語言

### 英文定位

> **A personal morning newspaper for everything you want to learn.**

### 中文定位

> **每天一壺，替你把開放網路煮成自己的晨報。**

### 品牌語言

> **網路不停說，你不用一直追。**

### 對開放網路的主張

不要把主要宣傳寫成「不需要購買付費知識」。這會不必要地把產品放進與付費課程對立的位置。

更穩健的說法是：

> **在購買更多知識以前，先把開放網路上已經存在的好內容真正讀懂、保存並記住。**

付費內容仍然可能提供系統性、原創研究與專家經驗；本產品的價值是先替使用者處理開放網路中的選擇、上下文、理解與記憶問題。

### 網站語言的使用方式

定位不只放在首頁的大標題。它應該像背景音一樣，分散在使用者每天會經過的地方；每一處各自說一小句，讓使用者慢慢熟悉這個產品，也讓第一次來的人很快知道 Brew 在照顧什麼。

| 位置 | 目前採用的語句 | 這句話負責的工作 |
| --- | --- | --- |
| 品牌副標 | 每天一壺 · 留下值得讀懂的東西 | 讓產品名稱帶著日常習慣與長期價值 |
| 今日手沖主文案 | 每天一壺，替你把開放網路煮成自己的晨報。 | 說清楚產品正在替使用者完成什麼 |
| 編輯註記 | 網路不停說，你不用一直追。 | 安放使用者的 FOMO，給他一點喘息 |
| 再手沖一批 | 看不夠，再泡一壺。 | 讓探索感成為產品動作的一部分 |
| 知識儲藏室 | 這些內容會慢慢長成你的知識庫。 | 把保存與複習說成長期累積 |
| 過往手沖 | 每一壺都會留下來。 | 讓過去的內容有回來的理由 |
| 我的配方 | 調一調你的晨報配方 | 讓使用者看見這些設定真的會改變每一壺的味道 |
| 頁尾 | 今天讀得懂，過些日子還用得上。 | 把短期閱讀連到長期使用 |

語言規則：

- 使用自然、短而有畫面的陳述句。
- 每個區域只承擔一個訊息，不把完整產品說明塞進同一句話。
- 讓「晨報、手沖、味道、留下來、回來」成為可持續使用的詞彙。
- 保留一點空白與餘韻，讓使用者自己感覺到產品的價值。
- 產品語言以陪伴與提醒為主，少用制式的比較句、宣講句與功能清單。

### 使用者任務（Job to be Done）

> 當我早上想學點有用的東西時，給我一小批符合我現在興趣與程度、來源可追溯、今天真的讀得完，而且以後還能重新複習的內容。

## 4. 轉型原則

1. **選擇比數量重要**：不要因為每天內容很多，就把更多內容塞給使用者。
2. **證據先於摘要**：每篇學習內容都必須保留原始來源、日期與可檢查的證據。
3. **設定要被看見成一份晨報配方**：它決定每一壺的味道，會隨著使用者的回饋慢慢變得精準。
4. **Prompt 負責描述語意喜好**：硬性來源限制、排除規則與存取權限由程式實際執行。
5. **模型負責理解與提煉**：來源收集、硬性過濾、去重與證據檢查保持可驗證。
6. **每一壺都要被保存**：個人晨報不能只是一次 API 回應；必須可以重新載入、回顧與複習。
7. **回饋要改變下一壺**：Starred、Super Starred、不感興趣等動作都必須成為未來推薦訊號。
8. **先做 Vibe Coding，架構預留擴張**：先證明一個主題上的個人化體驗，再逐步增加其他知識領域。
9. **API key 永遠留在伺服器端**：使用者偏好可以同步，金鑰不能暴露在前端或 Git。
10. **來源取得必須誠實**：無法合法或可靠取得的來源，就顯示無法取得，不要假裝讀過。

## 5. 目前系統與轉型缺口

### 目前已經具備的能力

- 今日手沖與固定篇數的學習內容。
- 偏好設定：來源權重、指定來源、額外 Prompt、硬性網址、語言。
- `/api/brew` 即時手沖。
- `server.mjs` 與 `api/brew.mjs` 的來源偏好與模型格式處理。
- Starred、Super Starred、知識儲藏室與歷史手沖。
- 難度標籤：初學者、普通、困難。
- 每日批次腳本與日期化輸出。
- 不收信箱的匿名晨報帳號，以及只用來稱呼使用者的暱稱。
- 獨立的「我的配方」頁面，顯示主題、內容口感、來源與每日閱讀節奏。

### 目前必須改變的地方

| 現在的做法 | 轉型後的做法 |
| --- | --- |
| 偏好主要存在瀏覽器 `localStorage` | 偏好成為使用者資料，`localStorage` 只作快取 |
| 每次手沖都可能重新生成 | 先建立並保存個人的 edition，再重新載入 |
| 全站共用 `latest.json` | 每位使用者、每天各自擁有一個 edition |
| 每日腳本產生單一批次 | 先建立候選內容池，再依使用者生成個人批次 |
| Starred 主要是收藏狀態 | 收藏、跳過與回饋會影響推薦排序 |
| 模型自行搜尋與整理 | 來源收集、驗證、排序與模型提煉分層 |
| 靜態頁面內含示範 lessons | 由個人 edition API 提供主要內容，保留示範資料作離線 fallback |

## 6. 目標生成流程

未來每一壺晨報應該遵循這條流程：

```text
使用者偏好與歷史回饋
        ↓
來源收集與候選內容池
        ↓
硬性過濾：日期、語言、網址、權限、排除項目
        ↓
證據檢查：URL、作者、日期、互動與來源完整性
        ↓
個人化排序：主題、來源、難度、新鮮感、複習與多樣性
        ↓
模型提煉：問題、原則、範例、限制、練習與證據
        ↓
結構化驗證與保存
        ↓
今日晨報、知識儲藏室與 Second Pour
```

模型只負責把已經選好的候選內容整理成學習素材，不應該完全自由決定所有來源、日期與證據。

目前已完成一個可驗收的分層版本：手沖前先由 GitHub、Hacker News、Reddit RSS、DEV.to 與公開 RSS 連接器收集候選；模型整理後統一進入 `candidate-pool-v1`，程式會做 URL 可訪問性、日期、證據、排除主題、難度、硬性網址、重複 URL 與重複概念檢查，再依使用者配方與回饋排序，最後才保存 edition。沒有合法公開連接器的來源會明確標記為 unsupported，不進行假爬取。

### 個人化排序至少需要考慮

- Curator 基礎分數。
- 主題符合度。
- 來源偏好。
- 難度符合度。
- 新鮮程度。
- 是否讀過。
- 是否收藏。
- 是否該複習。
- 來源與類別多樣性。
- 使用者過去的「不感興趣」訊號。

### 必要的硬性檢查

- [x] URL 可訪問或狀態明確標示。
- [x] 發布日期正確。
- [x] 不超過晨報資料截點。
- [x] 不重複同一來源。
- [x] 不重複同一個觀念。
- [x] 每篇都有來源證據。
- [x] 不捏造作者、日期、互動數據或引文。
- [x] 輸出符合固定 JSON schema。
- [x] 生成失敗時不發布 placeholder 內容。

## 7. 執行清單

### 第一階段：先定義「我的晨報」

- [x] 保留 Vibe Coding 作為第一個主題，不一開始就做所有知識領域。
- [x] 架構支援未來加入設計、創業、研究、心理學等主題。
- [x] 定義預設晨報配方：
  - 6 篇符合偏好的新發現。
  - 2 篇過去收藏的複習。
  - 1 篇經典內容。
  - 1 篇意外驚喜。
- [x] 讓使用者選擇每天閱讀時間：5、10、20 分鐘。
- [x] 讓使用者選擇每天篇數：5、10、15 篇。
- [x] 第一版不要讓使用者調整二十個參數。
- [x] 第一版先詢問：
  - 我想學什麼？
  - 我不想看到什麼？
  - 我偏好的來源？
  - 我想要多難？
  - 我想要多少新鮮感？
  - 我是否想複習舊內容？

第一階段的程式、資料契約與逐項檢查方式記錄在 [`第一階段-我的晨報驗收.md`](./第一階段-我的晨報驗收.md)。Supabase 專案與環境變數接上後，才算完成實際寄信與雲端寫入驗證。

### 第二階段：把偏好變成真正的使用者資料

- [x] 使用者帳號：先建立不要求信箱的匿名使用者 ID；目前會綁在這個瀏覽器的登入狀態。
- [x] 個人稱呼資料表：暱稱只負責讓報紙知道怎麼稱呼你，真正辨認資料的是匿名帳號 ID。
- [x] 個人偏好資料表：保存成使用者自己的晨報配方。
- [x] 個人晨報資料表：`brew_editions` 與 `brew_edition_items` 已建立，保存 daily、manual、historical edition。
- [x] 個人收藏與回饋資料表：`brew_item_marks` 與 `brew_feedback_events` 已建立，RLS 依使用者隔離。
- [x] 個人複習佇列：`brew_review_queue` 已建立，收藏會排入 Second Pour。
- [x] 使用者重新整理時載入原本的 edition，保持同一壺內容；daily edition 會先查詢再決定是否生成。
- [x] 將 `localStorage` 降級為本地快取；偏好、edition、收藏與複習的正式資料源是 Supabase。

### 建議資料結構


最重要的定義：


不能再只有一個全站共用的 `latest.json`。

#### 第二階段本次實作：不用信箱的暱稱帳號與「我的配方」

這次先把「人」與「配方」接起來，但不要求使用者交出電子郵件。使用者進入帳號入口時，只需要回答：

> **晨報怎麼稱呼你？**

系統會在背後建立一個匿名帳號 ID，並把暱稱保存成一個友善的顯示名稱。報紙可以寫成「小明的晨報」，但暱稱本身不是密碼，也不是可以拿來冒充別人的登入憑證；同名的人仍然是不同帳號。

目前的資料關係是：

```text
匿名帳號 ID
├── brew_profiles       → 報紙怎麼稱呼你
└── brew_preferences    → 這個人的晨報配方
```

使用者流程：

```text
我的晨報
→ 輸入暱稱
→ 建立匿名帳號
→ 保存暱稱
→ 查看／調整我的配方
→ 下一次手沖套用這份配方
```

畫面上也不再把這份重要資料藏在「偏好」裡：導覽列會直接出現「我的配方」，先顯示主題、內容口感、來源與每天的閱讀節奏；更細的來源、提示詞、硬性網址與生成方式才放在「配方細節」。

這個版本刻意保留一個誠實的邊界：匿名帳號沒有信箱或其他可找回的身份。如果使用者清除瀏覽器資料、登出或換裝置，單靠暱稱不能找回原本的配方。未來若真的需要跨裝置找回，必須另外設計使用者願意接受的連結方式，不能偷偷把信箱當成必要條件。

本次實作驗收：

- [x] 帳號入口不再要求電子郵件。
- [x] 使用者可以用暱稱建立晨報帳號。
- [x] 暱稱與配方都由後端依驗證後的帳號 ID 保存。
- [x] 使用者登入後可以直接查看自己的配方摘要。
- [x] 「偏好」被轉成獨立的「我的配方」與「配方細節」體驗。
- [x] 個人每天的 `edition` 與每次自動生成履歷已保存；本次仍把每日自動遞送列為後續工作，兩者不混為一談。

#### 第二階段追加：記錄每一次自動日報的生成配方

> 註記：第二階段原本的使用者資料與個人日報工作已接近完成。本段是追加內容，不取代原本的第二階段清單；本段目前只處理「每天自動生成的日報」，不處理手動手沖。

第二階段追加的核心不是只保存「今天生成了 10 篇」，而是要保存「這 10 篇是怎麼生成出來的」。每一次自動日報都要留下當時的完整生成履歷，讓日報不再是一個無法解釋的結果，而是一套可以閱讀、複製與分享的配方。

每一次自動生成應記錄：

- 這次生成的日期、資料截止日與生成時間。
- 當時使用的個人偏好配方，例如主題、來源、新鮮度、語言與篇數。
- 當時實際使用的完整提示詞，以及提示詞版本。
- 使用的模型、生成方式與搜尋規則。
- 這次生成是否成功、生成了哪 10 篇，以及每篇的來源。
- 這次生成所屬的日報，讓「一批 10 篇」和「生成這一批的流程」永遠連在一起。

過往日報除了可以查看當天的 10 篇內容，也應該可以查看：

```text
查看本期配方
→ 查看當時的偏好
→ 查看當時的提示詞
→ 查看當時使用的模型與來源規則
→ 複製或分享這套配方
```

分享時要提供一份安全的公開版本：移除 API 金鑰、私人資料與不想公開的個人偏好，只留下可以讓別人理解並嘗試的提示詞、配方與流程。使用者可以像在社群上分享一段「咒語」：

```text
我用這套日報配方與提示詞，生成出了一份高品質的每日報紙。
```

這裡追求的是「可理解、可重做、可分享的生成方法」，不是保證每次都產生完全一樣的內容。因為來源、模型與當天資料會改變，同一套配方應該產生相近的方法與品質，但不一定複製出完全相同的 10 篇。

追加驗收條件：

- [x] 每次自動生成 10 篇時，都建立一筆可追蹤的生成履歷；目前先保存到每日輸出下的 `generation-runs/` JSON。
- [x] 日報保存當時的偏好、提示詞、提示詞版本、模型與來源規則副本；每日 edition 會嵌入 `generation_recipe`。
- [x] 後端提供 `/api/edition-recipe?date=YYYY-MM-DD`，回傳移除私密資料後的日報配方副本。
- [x] 可以從 API 與「本期配方」視窗取得可複製的分享短句、公開配方與分享連結。
- [x] 舊日報檔案會保留當時嵌入的配方，不會因為之後修改目前配方而改寫；若用 `--force` 重跑同一天，則視為明確重新生成。
- [x] 今日與過往日報在具有自動生成履歷時，直接顯示「查看本期配方」與複製按鈕。
- [x] 手動手沖不列入本次追加範圍；介面只為 `automatic_daily_brew` 顯示公開配方，之後另行定義手動配方。

### 第三階段：深化我的配方

「我的配方」不只是設定頁，而是使用者可以理解、調整、回顧的「晨報配方」。

- [x] 主題權重：1–5。
- [x] 來源權重：1–5。
- [x] 指定來源。
- [ ] 排除來源：目前可用「少看這個來源」回饋影響下一壺；永久偏好黑名單仍待補上。
- [x] 指定社群或網址。
- [x] 分開軟性偏好與硬性規則。
- [x] 來源語言。
- [x] 輸出語言。
- [x] 難度。
- [x] 閱讀時間。
- [x] 新鮮內容與經典內容比例。
- [x] 複習比例。
- [x] 額外 Prompt。
- [x] 不想再看到的主題。

明確區分：

```text
偏好：請多找 GitHub、少找 Reddit
硬性規則：只能從這幾個網址翻找
```

Prompt 可以處理「語意喜好」，但不能取代真正的過濾、排序與權限規則。

### 第四階段：把生成流程拆成四層

目前比較像：

```text
呼叫模型 → 模型搜尋 → 模型整理 → 回傳
```

未來應該是：

```text
來源收集
→ 候選內容池
→ 硬性過濾與證據檢查
→ 個人化排序
→ 模型提煉成晨報
→ 儲存
```

### 第五階段：建立來源連接器

建議順序：

1. GitHub Discussions、Issues、Repositories。
2. Hacker News。
3. Reddit。
4. RSS 與公開技術部落格。
5. 使用者自行提供的網址。
6. Facebook 公開頁面或有合法存取權限的內容。

Facebook 社團不能直接假設可以任意爬取。穩妥做法是：

- [x] 使用者提供公開網址。
- [ ] 使用官方 API 或合法授權：目前尚未接 Facebook 等需要授權的來源。
- [ ] 提供手動匯入連結：目前先保留「無法取得」狀態，手動匯入另列工作。
- [x] 對無法讀取的內容清楚顯示「無法取得」或 `unsupported`。
- [x] 不假裝已經讀過無法驗證的社團內容。

### 第六階段：讓回饋真正影響下一壺

目前 Starred 與 Super Starred 已經同時是收藏狀態與下一壺的推薦訊號：

- [x] Starred：我想保存。
- [x] Super Starred：這非常符合我的口味。
- [x] 不感興趣：降低類似內容。
- [x] 不想看這個來源：先以回饋訊號降低同來源內容。
- [x] 想看更多這種內容。
- [ ] 已讀但不需要複習：目前可跳過複習，獨立的「不再排入」選項仍待補上。
- [x] 標記為想實作。

每個動作都記錄：

```text
使用者
內容
來源
主題
難度
動作
時間
```

系統最後要能理解：

> 系統最後要能理解：這個人喜歡 GitHub 上的實作失敗分析，來源偏好只是其中一個線索。

### 第七階段：做 Second Pour

這會讓產品從「摘要工具」變成「個人學習系統」。

簡單版本：

- [x] Starred：7 天後複習。
- [x] Super Starred：3 天、14 天、45 天複習。
- [x] 普通內容：閱讀後 30 天安排複習。
- [x] 複習時只顯示一個 30 秒問題，不重新塞完整文章；卡片可先想起來，再選擇打開原文、已複習或稍後再喝。
- [x] 每篇顯示「你在 24 天前讀過這個」類型的讀取日期與回訪次數。

複習問題範例：

> 還記得這個原則解決什麼問題嗎？

## 8. 最推薦的開發順序

不要一開始就做完整的「全世界知識平台」。

### MVP 1：單一使用者個人化

- [x] 個人主題。
- [x] 個人來源權重。
- [x] 個人難度。
- [x] 個人晨報。
- [x] 可保存與重新載入。
- [x] Brew another pot。
- [x] 仍然只支援 Vibe Coding 作為第一個產品主題，主配方目錄已預留科技相關擴張。

### MVP 2：個人回饋

- [x] Starred、Super Starred 的資料保存與 Second Pour 排程；`not_interested` API 動作也已納入資料契約。
- [x] 下一壺的候選排序會讀取 Starred、Super Starred、want_more、not_interested 與 exclude_source；排序快照會保存於該壺的 `generation_recipe.candidate_pool`。仍需用真實模型生成做一次人工驗收，確認差異符合直覺。
- [x] Pantry 與 Second Pour 的資料讀取，以及 30 秒回想卡片。

### MVP 3：真正多使用者

- [x] 登入。
- [x] 資料庫。
- [x] 每人不同的 edition。
- [x] 每人自己的歷史與複習資料。
- [x] 時區與晨報時間會保存於個人配方；真正按照每個人的時間自動送達仍屬 MVP 4。

### MVP 4：自動遞送

- [ ] 每日排程。
- [ ] Email 或通知。
- [ ] 失敗重試。
- [ ] 成本與使用量記錄。

### 推薦路徑

先完成 MVP 1，驗證「人們是否真的喜歡自己的晨報配方」；接著完成 MVP 2，驗證回饋是否能帶來更高的回訪與閱讀；最後才投入登入、資料庫與多人基礎設施。

## 9. 最小可驗收標準

當以下事情都成立，就有第一版真正的個人化晨報：

- [x] 新使用者可以完成偏好設定。
- [ ] 兩個不同使用者得到不同內容。
- [x] 相同使用者重新整理，不會重新生成另一壺；同日 daily edition 會被重載。
- [x] 使用者可以手動 Brew another pot；manual edition 會遞增 `pot_number`。
- [x] 每篇即時生成內容都有來源、日期、證據與難度；缺少這些欄位時整壺不保存。
- [x] Starred 會進入下一次候選排序；Super Starred 會給相似內容更高回饋分數。
- [x] Super Starred 會進入複習佇列。
- [x] 可按收藏、類別、難度瀏覽。
- [x] 使用者的偏好不會暴露 API key；快照保存前也會移除憑證樣式字串。
- [x] 生成失敗時不會塞入假文章或假來源；生成完成前不保存 edition。
- [x] 已登入的個人晨報不再依賴 Git 裡的單一 `latest.json`；未登入者仍保留示範／歷史 fallback。

## 11. 轉型成功的判準

產品成功的樣子，是每天產出的內容更貼近使用者，也更值得留下來。

成功是：

> 使用者早上打開 Brew，覺得這壺內容像是「有人真的懂我現在想學什麼」；讀完之後，知道哪些內容值得保存，也相信重要的內容未來還會在適合的時候回來。

這就是從每日摘要系統轉型為個人晨報與個人學習記憶系統的核心。
