# 第一階段驗收：我的晨報

這份文件用來檢查「我的晨報」第一階段的配方基礎。網站仍以 Vibe Coding 為第一份報紙，但登入後已能從五份固定科技主配方開始調配自己的晨報。帳號入口不收信箱，使用者只留下晨報稱呼，自己的主配方、編輯語氣、沖煮方式與早晨份量會保存到 Supabase。未登入者仍可閱讀與手沖原有內容。

## 七個驗收框

- [x] **Vibe Coding 是第一份報紙。** 五份主配方中的第一份是 Vibe Coding 入門；目前仍把內容範圍收在科技與初學者容易進入的方向。
- [x] **固定主配方可以擴充。** `morning-brew-recipes.mjs` 集中管理五份主配方，`recipe_id` 保存選擇；未來增加新方向時不必改資料表結構。第一版不開放任意混搭。
- [x] **有清楚的預設配方。** 登入後的配方介面顯示「6 篇新發現、2 篇收藏複習、1 篇經典、1 篇意外驚喜」；本機與 Vercel 的手沖提示都會收到 60／20／10／10 的方向。
- [x] **閱讀時間可選 5／10／20 分鐘。** 值會保存為 `reading_minutes`。
- [x] **每天篇數可選 5／10／15 篇。** 值會保存為 `item_count`，本機與 Vercel 手沖都接受最多 15 篇。
- [x] **沒有一次攤開二十個參數。** 第一次建立帳號只先問「晨報怎麼稱呼你？」；接著分三步選主配方、編輯語氣／沖煮方式，再設定早晨份量。來源網址、權重與 Prompt 留在「來源櫃」。
- [x] **晨報的核心選擇都有資料。** 主配方=`recipe_id`；編輯口感=`editorial_tone`；沖煮方式=`brew_method`；想學什麼與預設範圍來自主配方；不想看到什麼=`excluded_topics`；來源偏好與硬性來源留在來源櫃；難度=`difficulty_levels`；新鮮感=`novelty_level`；是否複習=`review_enabled`。

## Supabase 接線

目前已建立獨立的 Supabase 專案並套用 migration：

- 專案名稱：`brew`
- Project Ref：`syqtavpbobeqirsbgppp`
- 地區：東京 `ap-northeast-1`
- 正式網站：`https://brew-lime.vercel.app/`
- Vercel 的 Production、Preview、Development 已設定 `SUPABASE_URL` 與 `SUPABASE_PUBLISHABLE_KEY`。
- 本機 `.env.local` 已接上相同專案；該檔案不會進入 Git。

要使用不收信箱的帳號，仍需在 Supabase Dashboard 開啟匿名登入。現有連接器無法修改這項 Auth 設定，因此要手動設定一次：

1. 開啟 Supabase 專案 `brew`。
2. 進入 Authentication → URL Configuration。
3. 在 Authentication → Providers／General configuration 開啟 `Allow anonymous sign-ins`。
4. Site URL 仍可填入 `https://brew-lime.vercel.app/`；匿名登入不需要寄信回跳網址。

以下保留為重新接線時的完整順序：

1. 在 Supabase 建立或選定 Brew 專案。
2. 在 Supabase Auth 開啟 `Allow anonymous sign-ins`。
3. 依序套用這三份 migration：
   - `supabase/migrations/20260821134423_create_brew_preferences.sql`
   - `supabase/migrations/20260821160000_create_brew_profiles.sql`
   - `supabase/migrations/20260821190000_add_morning_brew_recipe_settings.sql`
4. 在本機 `.env.local` 與 Vercel Environment Variables 設定：

   ```text
   SUPABASE_URL=https://你的專案代號.supabase.co
   SUPABASE_PUBLISHABLE_KEY=你的 publishable key
   ```

5. 不要把 `service_role` key 放進網站、Git、`.env.example` 或瀏覽器。這套流程不需要它。

## 本機檢查

### 1. 靜態檢查

在 PowerShell 執行：

```powershell
node --check api/auth.mjs
node --check api/preferences.mjs
node --check api/brew.mjs
node --check morning-brew-recipes.mjs
node --check api/recipe-catalog.mjs
node --check api/edition-recipe.mjs
node --check server.mjs
node scripts/test-daily-recipe.mjs
node --input-type=module -e "import fs from 'node:fs'; import vm from 'node:vm'; const html=fs.readFileSync('outputs/vibe-coding-daily-brew/index.html','utf8'); const start=html.lastIndexOf('<script>'); const end=html.indexOf('</script>', start); new vm.Script(html.slice(start + 8, end)); console.log('inline script: OK');"
git diff --check
```

### 2. 啟動本機 API

```powershell
node server.mjs
```

另開一個 PowerShell 視窗執行：

```powershell
$healthResponse = Invoke-RestMethod http://localhost:4173/api/health
$recipeCatalogResponse = Invoke-RestMethod http://localhost:4173/api/recipe-catalog
$sourceResponse = Invoke-RestMethod 'http://localhost:4173/api/source-recommendations?recipe_id=ai-creative&limit=10'
[pscustomobject]@{
  health_ok = $healthResponse.ok
  recipe_count = $recipeCatalogResponse.recipes.Count
  tone_count = $recipeCatalogResponse.tones.Count
  method_count = $recipeCatalogResponse.methods.Count
  scoped_source_count = $sourceResponse.catalog_sources.Count
} | ConvertTo-Json
```

應看到 `health_ok: true`、`recipe_count: 5`、`tone_count: 3`、`method_count: 3` 與 `scoped_source_count: 10`。登入與保存流程則由使用者自行在本機頁面點測：輸入暱稱後依序走完三步，選擇 Vibe Coding 入門以外的主配方，再確認摘要顯示主配方、語氣與沖煮方式；保存後重新載入，Supabase 的同一個匿名帳號應帶回相同設定。

### 3. 資料庫檢查

在 Supabase SQL Editor 執行唯讀查詢：

```sql
select
  user_id,
  topics,
  excluded_topics,
  content_styles,
  source_lanes,
  difficulty_levels,
  recipe_id,
  editorial_tone,
  brew_method,
  source_language,
  selected_source_ids,
  source_weights,
  specific_sources,
  direct_urls,
  source_prompt,
  reading_minutes,
  item_count,
  novelty_level,
  review_enabled,
  onboarding_completed,
  updated_at
from public.brew_preferences
order by updated_at desc;
```

再檢查暱稱資料：

```sql
select user_id, nickname, updated_at
from public.brew_profiles
order by updated_at desc;
```

每個帳號應各有一列。前端送來的 `user_id` 不會被採用；後端會先向 Supabase 驗證 Access Token，再以驗證後的使用者 ID 讀寫。資料表已啟用 RLS，登入者只可讀寫自己的列。

## 已知邊界

- 這一階段保存的是「個人晨報配方」與「晨報稱呼」。自動日報與歷史手沖會保存當次的配方快照；每人每天一份、可跨裝置讀取的個人 `edition` 仍屬後續的多人資料架構。
- 2 篇收藏複習的配方已進入生成規則，但真正的個人複習佇列與 Second Pour 排程仍屬後續階段。候選不足時，生成器必須用可驗證的新發現補位，不得捏造收藏狀態。
- 匿名帳號綁在目前瀏覽器；清除瀏覽器資料、登出或換裝置後，單靠暱稱無法找回原本的配方。若未來要跨裝置找回，必須另設計使用者同意的連結方式。
