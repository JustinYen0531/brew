# 第一階段驗收：我的晨報

這份文件用來檢查「我的晨報」第一階段的配方基礎。網站仍以 Vibe Coding 為第一份報紙；目前帳號入口已改成不收信箱的匿名帳號，使用者只留下晨報稱呼，並把自己的晨報配方保存到 Supabase。未登入者仍可閱讀與手沖原有內容。

## 七個驗收框

- [x] **Vibe Coding 是第一個主題。** 晨報生成提示與既有分類仍以 Vibe Coding 為範圍，沒有把第一版擴成全知識平台。
- [x] **可擴充新的知識領域。** `topics` 使用字串陣列保存；加入設計、創業、研究或心理學時，不必改資料表結構。第一版介面只提供 Vibe Coding 內的細分標籤。
- [x] **有清楚的預設配方。** 登入後的配方介面顯示「6 篇新發現、2 篇收藏複習、1 篇經典、1 篇意外驚喜」；本機與 Vercel 的手沖提示都會收到 60／20／10／10 的方向。
- [x] **閱讀時間可選 5／10／20 分鐘。** 值會保存為 `reading_minutes`。
- [x] **每天篇數可選 5／10／15 篇。** 值會保存為 `item_count`，本機與 Vercel 手沖都接受最多 15 篇。
- [x] **沒有一次攤開二十個參數。** 第一次建立帳號只先問「晨報怎麼稱呼你？」；接著只出現一張「調配我的晨報」介面，較進階的來源網址、權重與 Prompt 留在「配方細節」。
- [x] **六個核心問題都有資料。** 想學什麼=`topics`；不想看到什麼=`excluded_topics`；偏好來源=`source_lanes`；難度=`difficulty_levels`；新鮮感=`novelty_level`；是否複習=`review_enabled`。

## Supabase 接線

目前已建立獨立的 Supabase 專案並套用 migration：

- 專案名稱：`brew`
- Project Ref：`syqtavpbobeqirsbgppp`
- 地區：東京 `ap-northeast-1`
- 正式網站：`https://brew-lime.vercel.app/`
- Vercel 的 Production、Preview、Development 已設定 `SUPABASE_URL` 與 `SUPABASE_PUBLISHABLE_KEY`。
- 本機 `.env.local` 已接上相同專案；該檔案不會進入 Git。

要使用不收信箱的帳號，仍需在 Supabase Dashboard 開啟匿名登入。現有連接器無法修改這項 Auth 設定，因此要手動設定一次：

1. 開啟 Supabase 專案 `brew`。
2. 進入 Authentication → URL Configuration。
3. 在 Authentication → Providers／General configuration 開啟 `Allow anonymous sign-ins`。
4. Site URL 仍可填入 `https://brew-lime.vercel.app/`；匿名登入不需要寄信回跳網址。

以下保留為重新接線時的完整順序：

1. 在 Supabase 建立或選定 Brew 專案。
2. 套用 `supabase/migrations/20260821134423_create_brew_preferences.sql`。
3. 在 Supabase Auth 開啟 `Allow anonymous sign-ins`。
4. 依序套用這兩份 migration：
   - `supabase/migrations/20260821134423_create_brew_preferences.sql`
   - `supabase/migrations/20260821160000_create_brew_profiles.sql`
5. 在本機 `.env.local` 與 Vercel Environment Variables 設定：

   ```text
   SUPABASE_URL=https://你的專案代號.supabase.co
   SUPABASE_PUBLISHABLE_KEY=你的 publishable key
   ```

6. 不要把 `service_role` key 放進網站、Git、`.env.example` 或瀏覽器。這套流程不需要它。

## 本機檢查

### 1. 靜態檢查

在 PowerShell 執行：

```powershell
node --check api/auth.mjs
node --check api/preferences.mjs
node --check api/brew.mjs
node --check server.mjs
git diff --check
```

### 2. 啟動網站

```powershell
node server.mjs
```

打開 `http://localhost:4173/`，依序檢查：

1. 右上角出現「登入／我的晨報」。
2. 打開右上角「我的晨報」，輸入一個暱稱。
3. 確認畫面顯示「晨報怎麼稱呼你？」而不是收信信箱。
4. 首次建立帳號後自動打開「調配我的晨報」。
5. 確認看得到預設配方 6／2／1／1，以及 5／10／20 分鐘、5／10／15 篇。
6. 選擇主題、排除主題、來源、難度、新鮮感與複習，再保存。
7. 點導覽列「我的配方」，確認看得到自己的配方摘要。
8. 重新整理頁面，確認同一個瀏覽器仍載入剛才的配方與暱稱。
9. 按「手沖」，確認請求篇數跟隨保存的 `item_count`。
10. 清除瀏覽器資料後重新建立另一個暱稱，確認這是新的匿名帳號；單靠相同暱稱不會讀到上一個帳號的配方。

### 3. 資料庫檢查

在 Supabase SQL Editor 執行唯讀查詢：

```sql
select
  user_id,
  topics,
  excluded_topics,
  content_styles,
  source_lanes,
  difficulty_levels,
  reading_minutes,
  item_count,
  novelty_level,
  review_enabled,
  onboarding_completed,
  updated_at
from public.brew_preferences
order by updated_at desc;
```

再檢查暱稱資料：

```sql
select user_id, nickname, updated_at
from public.brew_profiles
order by updated_at desc;
```

每個帳號應各有一列。前端送來的 `user_id` 不會被採用；後端會先向 Supabase 驗證 Access Token，再以驗證後的使用者 ID 讀寫。資料表已啟用 RLS，登入者只可讀寫自己的列。

## 已知邊界

- 這一階段保存的是「個人晨報配方」與「晨報稱呼」，還沒有建立每人每天一份的 `edition`；那屬於轉型藍圖第二階段後續工作。
- 2 篇收藏複習的配方已進入生成規則，但真正的個人複習佇列與 Second Pour 排程仍屬後續階段。候選不足時，生成器必須用可驗證的新發現補位，不得捏造收藏狀態。
- 匿名帳號綁在目前瀏覽器；清除瀏覽器資料、登出或換裝置後，單靠暱稱無法找回原本的配方。若未來要跨裝置找回，必須另設計使用者同意的連結方式。
