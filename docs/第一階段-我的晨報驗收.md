# 第一階段驗收：我的晨報

這份文件用來檢查「我的晨報」第一階段的配方基礎，以及目前已接上的個人晨報保存。網站仍以 Vibe Coding 為第一份報紙，但登入後已能從五份固定科技主配方開始調配自己的晨報。帳號入口不收信箱，使用者只留下晨報稱呼，自己的主配方、編輯語氣、沖煮方式與早晨份量會保存到 Supabase；生成後的個人 edition、每篇內容、收藏回饋與 Second Pour 也有自己的資料列。未登入者仍可閱讀與手沖原有內容。

## 七個驗收框

- [x] **Vibe Coding 是第一份報紙。** 五份主配方中的第一份是 Vibe Coding 入門；目前仍把內容範圍收在科技與初學者容易進入的方向。
- [x] **固定主配方可以擴充。** `morning-brew-recipes.mjs` 集中管理五份主配方，`recipe_id` 保存選擇；未來增加新方向時不必改資料表結構。第一版不開放任意混搭。
- [x] **有清楚的預設配方。** 登入後的配方介面顯示「6 篇新發現、2 篇收藏複習、1 篇經典、1 篇意外驚喜」；本機與 Vercel 的手沖提示都會收到 60／20／10／10 的方向。
- [x] **閱讀時間可選 5／10／20 分鐘。** 值會保存為 `reading_minutes`。
- [x] **每天篇數可選 5／10／15 篇。** 值會保存為 `item_count`，本機與 Vercel 手沖都接受最多 15 篇。
- [x] **沒有一次攤開二十個參數。** 第一次建立帳號只先問「晨報怎麼稱呼你？」；接著分三步選主配方、編輯語氣／沖煮方式，再設定早晨份量。來源網址、權重與 Prompt 留在「來源櫃」。
- [x] **晨報的核心選擇都有資料。** 主配方=`recipe_id`；編輯口感=`editorial_tone`；沖煮方式=`brew_method`；想學什麼與預設範圍來自主配方；不想看到什麼=`excluded_topics`；來源偏好與硬性來源留在來源櫃；難度=`difficulty_levels`；新鮮感=`novelty_level`；是否複習=`review_enabled`。

## Supabase 接線

目前已建立獨立的 Supabase 專案並套用 migration：

- 專案名稱：`brew`
- Project Ref：`syqtavpbobeqirsbgppp`
- 地區：東京 `ap-northeast-1`
- 正式網站：`https://brew-lime.vercel.app/`
- Vercel 的 Production、Preview、Development 已設定 `SUPABASE_URL` 與 `SUPABASE_PUBLISHABLE_KEY`。
- 本機 `.env.local` 已接上相同專案；該檔案不會進入 Git。

要使用不收信箱的帳號，仍需在 Supabase Dashboard 開啟匿名登入。現有連接器無法修改這項 Auth 設定，因此要手動設定一次：

1. 開啟 Supabase 專案 `brew`。
2. 進入 Authentication → URL Configuration。
3. 在 Authentication → Providers／General configuration 開啟 `Allow anonymous sign-ins`。
4. Site URL 仍可填入 `https://brew-lime.vercel.app/`；匿名登入不需要寄信回跳網址。

以下保留為重新接線時的完整順序：

1. 在 Supabase 建立或選定 Brew 專案。
2. 在 Supabase Auth 開啟 `Allow anonymous sign-ins`。
3. 依序套用這六份 migration：
   - `supabase/migrations/20260821134423_create_brew_preferences.sql`
   - `supabase/migrations/20260821160000_create_brew_profiles.sql`
   - `supabase/migrations/20260821190000_add_morning_brew_recipe_settings.sql`
   - `supabase/migrations/20260822100000_create_personal_brew_data.sql`
   - `supabase/migrations/20260822101000_add_personal_brew_fk_indexes.sql`
   - `supabase/migrations/20260822102000_allow_review_queue_cleanup.sql`
4. 在本機 `.env.local` 與 Vercel Environment Variables 設定：

   ```text
   SUPABASE_URL=https://你的專案代號.supabase.co
   SUPABASE_PUBLISHABLE_KEY=你的 publishable key
   ```

5. 不要把 `service_role` key 放進網站、Git、`.env.example` 或瀏覽器。這套流程不需要它。

### 3. 個人晨報 API 檢查

這一段不需要呼叫模型，可以先確認資料契約與隔離邏輯：

應看到尚未生成時 `edition: null`、歷史與儲藏室可以回傳空清單，而未帶 `Authorization` 的 personal API 應回傳 401。完成一壺手沖後再重讀同一日期，應回到原本的 edition；「再手沖」使用 `kind=manual`，同一天會保存為下一個 `pot_number`。收藏動作的驗收是：Starred 排 1 筆複習、Super Starred 排 3 筆複習、取消收藏後待複習排程為 0 筆。

### 5. 資料庫檢查

在 Supabase SQL Editor 執行唯讀查詢：

```sql
select
  user_id,
  topics,
  excluded_topics,
  content_styles,
  source_lanes,
  difficulty_levels,
  recipe_id,
  editorial_tone,
  brew_method,
  source_language,
  selected_source_ids,
  source_weights,
  specific_sources,
  direct_urls,
  source_prompt,
  reading_minutes,
  item_count,
  novelty_level,
  review_enabled,
  onboarding_completed,
  updated_at
from public.brew_preferences
order by updated_at desc;
```

再檢查暱稱資料：

```sql
select user_id, nickname, updated_at
from public.brew_profiles
order by updated_at desc;
```

每個帳號應各有一列。前端送來的 `user_id` 不會被採用；後端會先向 Supabase 驗證 Access Token，再以驗證後的使用者 ID 讀寫。資料表已啟用 RLS，登入者只可讀寫自己的列。

再檢查個人晨報資料表是否有 RLS：

```sql
select
  tablename,
  rowsecurity
from pg_tables
where schemaname = 'public'
  and tablename in ('brew_editions', 'brew_edition_items', 'brew_item_marks', 'brew_feedback_events', 'brew_review_queue')
order by tablename;

select
  edition_date,
  kind,
  pot_number,
  requested_count,
  jsonb_object_keys(generation_recipe) as recipe_field
from public.brew_editions
where user_id = auth.uid()
order by edition_date desc, pot_number desc;
```

`rowsecurity` 應為 `true`。`generation_recipe` 是該壺建立時的副本；API key 不應出現在其中，API key 只留在瀏覽器的本機 Key 欄位，後端也會在保存前移除憑證樣式字串。

Supabase Security Advisor 會對這五張表顯示匿名存取政策警告，原因是本產品刻意使用 Supabase Anonymous Sign-ins，而匿名使用者在資料庫層仍走 `authenticated` role；真正的資料隔離仍由 `auth.uid()` 的 RLS policy 執行。這不是把表開給 `anon` role，仍要持續確認 policy 沒有使用 `using (true)` 之類的全開條件。

## 已知邊界

- 個人 daily、manual、historical edition、內容項目、收藏回饋、候選池排序與 Second Pour 排程已接上 Supabase；仍需要實際模型生成驗證不同回饋是否產生肉眼可見的內容差異。
- 每個人的 edition 已能重讀與分開保存；每日自動遞送、獨立來源連接器與真正逐一發 HTTP 請求的來源可訪問性檢查仍是後續工作。候選不足時，生成器會直接失敗，不得捏造收藏狀態或來源。
- 匿名帳號綁在目前瀏覽器；清除瀏覽器資料、登出或換裝置後，單靠暱稱無法找回原本的配方。若未來要跨裝置找回，必須另設計使用者同意的連結方式。
